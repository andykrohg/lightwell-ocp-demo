From Vulnerable to Verified

Lightwell Network · Trusted Profile Analyzer · Advanced Cluster Security

Act 1 — The Problem
1

Build the Vulnerable App

A catalog microservice uses woodstox-core 6.0.3 for XML parsing. This version contains CVE-2022-40152 — a denial-of-service vulnerability where a tiny crafted XML document triggers unbounded recursion in the DTD parser, crashing the service.

make pipeline-vulnerable
What to show Watch the pipeline run in OpenShift. In the vex-check step logs, note that CVE-2022-40152 appears in the vulnerability list. No VEX data applies to the standard Maven Central version, so the CVE remains unresolved.

2

Examine the Results

The SBOM was uploaded to Trusted Profile Analyzer for tracking, and ACS flagged a policy violation for CVE-2022-40152. Since the policy is in inform mode, the app deployed despite the vulnerability.

What to show In TPA, find the catalog-app SBOM tagged vulnerable. In ACS, filter violations by namespace ${DEMO_NAMESPACE} and note the CVE-2022-40152 policy violation.
TPA — SBOM Browser ACS — Violations
Act 2 — The Fix
3

Lightwell Network: Drop-In Remediation

Lightwell provides the same dependency version with a backported security patch. No code changes, no API breaks — just a different Maven repository. The .rhlw suffix indicates a patched build.

woodstox-core  6.0.3  →  6.0.3.rhlw-00001

The patch adds a recursion depth limit of 500 to the DTD parser, eliminating the DoS vector. Lightwell also publishes VEX data declaring this package as not_affected for CVE-2022-40152.

make pipeline-remediated
What to show In the vex-check step logs, compare the summary: Suppressed by VEX: 1. CVE-2022-40152 is confirmed as patched and removed from the findings.
OpenShift — Pipeline Runs TPA — SBOM Browser
4

Live Exploit: CVE-2022-40152

Prove the remediation works functionally. A tiny XML payload (<1 KB) with deeply nested DTD declarations exploits unbounded recursion to crash the vulnerable app. The Lightwell-patched version rejects it at a depth limit.

./scripts/exploit-demo.sh http://<vulnerable-route> http://<remediated-route>
What to show The vulnerable app returns HTTP 500 (StackOverflowError) or crashes entirely. The remediated app handles the same payload cleanly — same version, same API, patched security posture.

Run from a terminal with access to the cluster routes.

Act 3 — Lock the Door
5

Enable VEX Enforcement

Now that a clean alternative exists, require VEX remediation data before builds proceed. Builds shipping unvetted dependencies — with zero VEX suppressions — are blocked.

make pipeline-enforce
What to show The vulnerable build is re-triggered with REQUIRE_VEX=true. Since the standard woodstox-core doesn't match any VEX statements, zero CVEs are suppressed and the vex-check step fails the build.
OpenShift — Pipeline Runs
6

The Full Supply Chain

With VEX enforcement in the pipeline and cosign image signing on every build, the supply chain is locked down:

  1. Pipeline vex-check — blocks builds without verified remediation data
  2. Cosign signing — only pipeline-built images are trusted
  3. ACS — monitors CVEs across deployments and enforces image signature verification
  4. TPA — tracks every SBOM and advisory for full supply chain visibility

Key Takeaways

  • Drop-in replacement — no code changes, just switch the Maven profile
  • CVE-2022-40152 eliminated at the dependency level by Lightwell Network
  • VEX data enables accurate vulnerability assessment, distinguishing patched from unpatched
  • Pipeline enforcement blocks builds with unresolved vulnerabilities
  • Image signing with Sigstore/cosign for supply chain integrity
  • Full SBOM visibility tracked and analyzed in Trusted Profile Analyzer
